# 05 技术复盘

> 本文是基于本次实现形成的技术复盘初稿。候选人应在真实运行和亲自审查后补充自己的学习收获，不应直接冒充个人经验。

## 最难的问题

第一，区分“有 Agent 外观”与“模型真正参与决策”。离线 Mock 很容易生成漂亮 Trace，但这只能测流程。因此真实适配器每轮把最新观察交还模型，编排器不预设必须搜索几次、读取哪篇；同时在评估文档中明确 Mock 的证据边界。真实服务运行还暴露了连续输出多个 JSON 动作的兼容问题，修复时只执行首个动作而不是预放后续动作，确保后续决策仍依赖新观察。

第二，引用支持不能只靠提示词。即使要求模型引用原文，也可能出现改写、拼接或引用未读取文档。因此结束动作增加程序校验，失败作为新观察反馈，且设置总步数上限。测试还故意提交错误 quote，验证防护确实生效。

第三，冲突不能变成排序题。D02 日期较新不代表自动覆盖 D01；在缺少适用范围与优先级时，正确输出是双方事实、引用、缺口和追问，而不是一个看似干脆但无依据的数字。

## 学习收获

- 工具观察应结构化，模型才能针对错误、空命中和多文档结果调整动作。
- 检索片段适合定位，最终答案应以原文读取为依据，两者分开更容易审计。
- 可靠性不仅是提示词，还包括协议校验、执行预算、故障注入和可复现测试。
- 替换资料测试比固定答案断言更能发现硬编码；本项目将 D03 从 500 改为 600，检查答案与引用同步变化。

## 下一步

1. 复跑并扩展真实模型成功与失败路径，针对新错误继续迭代提示、解析兼容和工具描述。
2. 引入带权限元数据的嵌入检索，与字符检索做召回对照，而不是直接假定向量检索更好。
3. 增加答案与引用语义一致性评估、更多冲突类型和跨轮上下文测试。
4. 若进入生产，再考虑权限隔离、文档版本生效范围、审计存储和限流，而非在当前小题中过度设计。
